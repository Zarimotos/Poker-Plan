# Правила совместной разработки

Источник командных договорённостей: [`docs/roadmap.md`](docs/roadmap.md), раздел 7, и ТЗ PRE-04.

## Ветки

- Начинай задачу от актуальной `develop`, не от `main`.
- Формат имени: `type/short-description`, например `feat/session-creation`, `docs/roadmap-update`, `chore/repo-setup`.
- Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.
- Не делай прямой push в `main` и `develop`, не переписывай их историю.

## Коммиты

Conventional Commits: `type(scope): description` или `type: description`.

Примеры:

```text
feat(session): add session creation endpoint
docs: update project roadmap
test(import): cover invalid CSV rows
chore: configure repository
```

Финальное сообщение Squash and merge должно описывать **всю задачу**.

## Pull Request

1. Открой PR из рабочей ветки в **develop** (проверь base branch).
2. Заполни шаблон: цель, результат, проверка, ограничения, при необходимости скриншоты.
3. При изменении API/моделей/интеграций заранее согласуй с затронутыми участниками.
4. Получи не менее одного одобрения **другого разработчика**. Автор не одобряет собственный PR.
5. Исправь блокирующие замечания; выполни настроенные автоматические проверки, а до появления CI явно запиши ручную проверку.
6. Используй **Squash and merge** для рабочих веток. Удали временную ветку после слияния.

Ревью распределено между разработчиками, тимлид не обязан проверять каждый PR.

## Релизы

- PR из `develop` (или специально подготовленной `release/...`) в `main` только после решения тимлида о составе и готовности релиза.
- Перенос между постоянными ветками: **Create a merge commit**, не Squash and merge.
- Поставь тег версии после выпуска (`v0.1.0` и т. п.).
- Если `develop` содержит незавершённую функциональность, не выпускай её целиком без проверки; изолируй или исключи из релиза.
- Для `hotfix/...` исправление из `main` нужно также перенести в `develop`.

## Документы и безопасность

- Документы, API, схемы и соглашения обновляются в том же PR, где устаревают.
- Не коммить реальные секреты и локальные конфигурации; добавляй только пример `.env.example`.
- Не загружай тяжёлые экспорты Figma без необходимости; храни ссылку на актуальный макет.
