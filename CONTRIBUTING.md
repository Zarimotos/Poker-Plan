# Внесение изменений в Planning Poker

Этот файл — **краткая практическая памятка** для работы с репозиторием. Полные договорённости об итерациях, готовности задач, проверках, Git и релизах находятся в [плане итеративной разработки продукта](docs/iteration-process.md). Функциональный объём спринтов определяется [продуктовым анализом](docs/product-analysis.md); контрольные точки — [дорожной картой](docs/roadmap.md).

## Перед началом работы

- Убедитесь, что понятны цель задачи, ожидаемый результат, границы и способ проверки. Для функциональных задач учитывайте согласованный уровень L1–L3 и DoR.
- Техническое проектирование — часть инженерной работы: заранее подготовленные схемы в [`docs/specs/`](docs/specs/) можно использовать как варианты реализации, а не как неизменяемые предписания.
- Если выбранное техническое решение меняет пользовательское поведение или продуктовые ограничения, согласуйте изменение до реализации. Общие API и форматы данных согласуйте с участниками, которых они затрагивают.

## Ветки

- Создавайте рабочую ветку от актуальной `develop`, а не от `main`.
- Используйте имена вида `type/short-description`, при необходимости с номером задачи: `feat/session-creation`, `fix/csv-preview`, `docs/update-project-guides`.
- Допустимые типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.
- Не отправляйте изменения напрямую в `develop` и `main`, не переписывайте историю общих веток.

## Коммиты

Используйте Conventional Commits: `type(scope): description` либо `type: description`.

```text
feat(session): add session creation endpoint
fix(import): handle duplicate task ids
docs: update project documentation
test(import): cover invalid CSV rows
chore: configure local tooling
```

Сообщение итогового squash-коммита должно описывать всю выполненную задачу.

## Pull Request и ревью

1. Откройте PR **из рабочей ветки в `develop`** и проверьте целевую ветку.
2. Заполните шаблон: цель, сделанные изменения, как проверяли результат, известные ограничения; для UI-изменений по возможности добавьте скриншот.
3. Получите не менее одного одобрения другого разработчика; автор не одобряет собственный PR. Ревью распределено между разработчиками и не требует участия тимлида в каждом PR.
4. Исправьте блокирующие замечания и пройдите настроенные проверки. До появления CI укажите ручную проверку и её результат.
5. Для рабочих веток используйте **Squash and merge**. После слияния временную ветку можно удалить.

Крупную функциональность можно интегрировать частями. При этом незавершённые части не должны ломать уже работающие сценарии или выглядеть как готовые функции.

## Релизы и исправления

- `main` содержит только согласованные и проверенные релизы.
- Перенос принятого релиза из `develop` в `main` выполняется через PR с **Create a merge commit**, не squash; выпуск помечается тегом версии (`v0.1.0` и т. п.).
- Нельзя автоматически выпускать все незавершённые изменения из `develop`.
- Для срочного исправления принятого релиза используйте `hotfix/...` от `main`, после чего обязательно перенесите исправление в `develop`.

## Документация и безопасность

- Обновляйте затронутые инструкции, API-договорённости и технические документы вместе с изменениями кода, делающими старую информацию неверной.
- Не смешивайте назначения трёх основных документов: продуктовый анализ — **что**, план итеративной разработки — **как**, дорожная карта — **когда и куда**.
- Не добавляйте секреты и реальные `.env` в Git. Используйте `.env.example`; для макетов предпочтительна ссылка на Figma, а не тяжёлые экспорты.
