# ТЗ: S1-08 · Визуальные области функций следующих итераций

**Статус:** рабочее ТЗ для разработки  
**Спринт:** 1 — «Скелет продукта»  
**Целевой уровень:** L1 — интерфейсный контур  
**Перенос:** Да — каркасы будущих возможностей не блокируют рабочий путь Host  
**Ответственный за продуктовые решения:** тимлид (PM/PO)  
**Ответственные за реализацию:** тимлид и разработчики  

## 1. Основная идея

В основных экранах однопользовательского сценария могут быть подготовлены визуальные области для функций следующих итераций: участники, исторические подсказки, таймер, комментарии и управление очередью. Эти области не должны имитировать работу функций и не должны мешать рабочему пути Host.

Неработающие элементы должны быть скрыты либо явно неактивны. Задача не требует реализации бизнес-логики, серверных данных или функций уровня L2.

## 2. Пользовательский сценарий

1. Host создаёт сессию и попадает в лобби.
2. Host видит основные рабочие элементы текущего сценария.
3. Host может увидеть визуальные области для будущих функций.
4. Неработающие элементы скрыты либо явно неактивны.
5. Host не может выполнить действия, которые относятся к будущим итерациям.
6. Host продолжает работать с реализованными функциями S1-01–S1-07.

## 3. Требования к поведению

### 3.1. Визуальные области будущих функций

- В основных экранах могут быть предусмотрены визуальные области для будущих функций.
- Допускаются области для:
  - участников;
  - исторических подсказок;
  - таймера;
  - комментариев;
  - управления очередью.
- Визуальные области не должны имитировать реальную работу функций.
- Визуальные области не должны содержать вымышленные данные, которые можно принять за реальные результаты.
- Визуальные области не должны блокировать основной пользовательский путь Host.

### 3.2. Скрытие и неактивность

- Неработающие элементы должны быть скрыты либо явно неактивны.
- Если элемент отображается, должно быть понятно, что он пока недоступен.
- Неактивные элементы не должны запускать несуществующие функции.
- Неактивные элементы не должны создавать впечатление, что функция уже работает.
- Если элемент скрыт, пользователь не должен иметь к нему доступа.

### 3.3. Приоритет основного сценария

- Рабочий путь Host имеет приоритет над визуальными областями будущих функций.
- Визуальные области не должны мешать созданию сессии, импорту CSV, просмотру очереди, оценке задачи, подтверждению SP и просмотру итогов.
- Если визуальная область мешает основному сценарию, она должна быть скрыта или удалена из текущей итерации.
- Визуальные области не должны нарушать уже работающие функции.

## 4. Обязательные данные

Для визуальных областей не требуется сохранение серверных данных.

Допустимо отображать:

- Статические подсказки о будущих функциях.
- Пустые состояния.
- Неактивные элементы интерфейса.
- Скрытые области для будущих функций.

Не допускается отображение:

- Вымышленных участников.
- Вымышленных исторических эталонов.
- Вымышленных комментариев.
- Вымышленных значений таймера.
- Вымышленных результатов оценки.

## 5. Ограничения и правила

- Задача имеет уровень L1.
- Не требуется реализация бизнес-логики.
- Не требуется сохранение данных на сервере.
- Не требуется подключение участников.
- Не требуется реализация исторических подсказок.
- Не требуется реализация таймера.
- Не требуется реализация комментариев.
- Не требуется реализация управления очередью.
- Не требуется имитация работы будущих функций.
- Визуальные области не должны блокировать основной пользовательский путь Host.

## 6. Ошибки и состояния

### 6.1. Неактивные элементы

- Если элемент не реализован, он должен быть скрыт либо явно неактивен.
- Неактивный элемент не должен запускать несуществующее действие.
- Неактивный элемент не должен приводить к ошибке выполнения.

### 6.2. Ошибка отображения

- Если визуальная область не может быть отображена, она не должна нарушать работу основного сценария.
- Основной пользовательский путь Host должен продолжать работать.
- Ошибка отображения визуальной области не должна блокировать создание сессии, импорт, оценку или итоги.

## 7. Критерии приёмки

### AC-1. Визуальные области не мешают основному сценарию

**Дано:** Host находится в лобби, очереди или на экране оценки.  
**Когда:** Host выполняет основной сценарий.  
**Тогда:** визуальные области будущих функций не блокируют создание сессии, импорт, оценку и просмотр итогов.

### AC-2. Неработающие элементы скрыты или неактивны

**Дано:** В интерфейсе предусмотрена область будущей функции.  
**Когда:** Host взаимодействует с интерфейсом.  
**Тогда:** неработающие элементы скрыты либо явно неактивны.

### AC-3. Нет имитации работы функций

**Дано:** В интерфейсе отображается визуальная область будущей функции.  
**Когда:** Host взаимодействует с интерфейсом.  
**Тогда:** область не содержит вымышленных данных и не имитирует реальную работу функции.

### AC-4. Неактивные элементы не запускают действия

**Дано:** В интерфейсе есть неактивный элемент будущей функции.  
**Когда:** Host пытается с ним взаимодействовать.  
**Тогда:** действие не выполняется, а элемент остаётся неактивным.

### AC-5. Основной сценарий остаётся работоспособным

**Дано:** В интерфейсе есть визуальные области будущих функций.  
**Когда:** Host выполняет полный однопользовательский сценарий.  
**Тогда:** создание сессии, импорт CSV, просмотр очереди, оценка и итоги работают без нарушений.

- Неработающие элементы могут быть скрыты с помощью условий отображения.
- Неактивные элементы могут быть реализованы через отключённое состояние интерфейса.
- Для будущих функций могут быть предусмотрены пустые состояния.
- Визуальные области не должны требовать серверных данных или бизнес-логики.
