# ТЗ: PRE-06 — Стратегия проверок и тестирования продукта

**Задача:** определить, что, когда, как и кем проверяется в Planning Poker: ключевые сценарии, виды ручных и автоматических проверок, моменты выполнения и ответственных. Результат должен сделать понятным, какие проверки стоит автоматизировать в CI.

**Владелец задачи:** системный аналитик.

**Основные исполнители:** системный аналитик, бэкенд-разработчик / DevOps, 2 фронтенд-разработчика.

**Участник:** дизайнер — определяет проверяемые UI-состояния и критерии соответствия макетам.

**Приоритет:** средний; стратегия может уточняться параллельно первой реализации, но готовые функции должны проверяться по DoD.

## Цель

К концу задачи команда получает единый подход к качеству: минимальный набор обязательных проверок для каждой задачи, регрессионный набор для ключевого сценария и перечень проверок, которые целесообразно автоматизировать в CI. Настройка самого CI и Docker в PRE-06 не входит.

**Ожидаемый результат по плану:** описаны проверяемые свойства и ключевые сценарии, виды ручных и автоматических проверок, моменты их выполнения и роли ответственных.

## Границы

| Входит | Не входит |
|---|---|
| Ключевые пользовательские сценарии | Реализация тестов |
| Проверяемые свойства продукта | Настройка CI |
| Ручные и автоматические проверки | Настройка Docker |
| Моменты выполнения проверок | Нагрузочное тестирование |
| Ответственные за проверки | Полное покрытие всех редких случаев |
| Перечень проверок для CI | Развертывание тестового стенда |
| Чек-листы приёмки задач | Автоматизация всех UI-сценариев |

Стратегия определяет подход к проверкам, а не создаёт тестовую инфраструктуру.

## Ключевые сценарии

Минимальный регрессионный набор строится вокруг первого сквозного сценария:

- **Создание сессии:** Host создаёт сессию, получает серверный идентификатор и попадает в лобби.
- **Импорт CSV:** Host загружает корректный CSV, видит предпросмотр, подтверждает импорт; задачи сохраняются на сервере.
- **Ошибки импорта:** пустой, невалидный или частично некорректный CSV обрабатывается понятным сообщением.
- **Очередь задач:** Host видит реально импортированные задачи в актуальном порядке.
- **Оценка задачи:** Host видит текущую задачу и выбирает числовую карту SP.
- **Фиксация SP:** Host подтверждает итоговый SP; значение сохраняется на сервере.
- **Переход между задачами:** после подтверждения можно перейти к следующей задаче.
- **Итоги:** после оценки задач Host видит результаты с реально сохранёнными итоговыми SP.
- **Восстановление состояния:** после обновления страницы сессия, задачи и подтверждённые оценки не теряются.
- **Базовые ошибки:** при сбое создания сессии, импорта, оценки или получения итогов пользователь получает понятную реакцию.

## Виды проверок

| Вид проверки | Что проверяет | Когда выполняется | Кто отвечает |
|---|---|---|---|
| Ручная приёмка сценария | Работает ли пользовательский путь от начала до конца | Перед переводом задачи в Done и перед демо | Автор задачи + ревьюер |
| Проверка UI по макетам | Соответствие экранов, состояний и текстов дизайну | Для UI-изменений перед PR/слиянием | Фронтенд + дизайнер |
| API-проверка | Корректность запросов, ответов, кодов и ошибок | При изменении бэкенда или контракта | Бэкенд |
| Интеграционная проверка | Совместная работа клиента и сервера | Для задач, затрагивающих клиент и сервер | Фронтенд + бэкенд |
| Юнит-тесты | Логика валидации, расчётов и преобразований | Локально и в CI после настройки | Автор изменения |
| Контрактные тесты | Соответствие API-контракту | При изменении API или моделей | Бэкенд + фронтенд |
| Регрессионный чек-лист | Не сломаны ли ключевые сценарии | Перед слиянием значимых изменений и перед релизом | Ревьюер + автор |
| Демонстрация спринта | Достигнут ли целевой результат итерации | В конце спринта / контрольной точке | Тимлид + команда |

Для задач, охватывающих клиент и сервер, обе части должны быть интегрированы и проверены на общем сценарии.

## Приоритеты автоматизации

Автоматизировать в первую очередь:

- валидацию CSV и преобразование CSV → `Task`;
- создание сессии и получение сессии по идентификатору;
- сохранение импортированных задач;
- выбор и фиксацию итогового SP;
- получение итогов сессии;
- базовые коды ошибок API;
- сборку фронтенда и бэкенда;
- линтеры и проверку типов, если они приняты в стеке.

Не автоматизировать на старте:

- визуальную полировку всех экранов;
- редкие сетевые сбои;
- полный E2E-прогон всех состояний;
- проверку будущих функций: WebSocket, участников, таймера, комментариев, эталонов и интеграций.

## Правила по уровням L1–L3

Проверки зависят от заявленного уровня задачи:

| Уровень | Минимальная проверка |
|---|---|
| L1 | Есть визуальный контур; неработающие элементы явно неактивны или скрыты; нет ложного впечатления работоспособности |
| L2 | Основной сценарий работает на реальных данных; базовые ошибки и состояния обработаны; результат сохраняется там, где это заявлено |
| L3 | Дополнительно проверяются граничные случаи, восстановление, устойчивость и согласованные расширения |

Наличие макета не делает функцию L2, а L2 не требует реализации всех нарисованных кнопок.

## Чек-лист задачи

Перед переводом задачи в Done автор и ревьюер проверяют:

- Реализовано поведение заявленного уровня L1/L2/L3.
- Нет незаявленных заглушек.
- Пройдены критерии приёмки из задачи.
- Обработаны базовые ошибки и состояния.
- Клиент и сервер интегрированы, если задача их затрагивает.
- Ключевые сценарии не сломаны.
- Изменения доступны в общей ветке `develop`.
- Документация обновлена, если изменились API, запуск или правила.
- Способ проверки указан в PR.

## Шаблон чек-листа по функциям

### Импорт CSV

- Корректный CSV импортируется.
- Предпросмотр показывает распознанные задачи.
- Отмена не изменяет очередь.
- Подтверждение создаёт реальные задачи на сервере.
- Пустой файл вызывает понятную ошибку.
- Невалидный CSV вызывает понятную ошибку.
- Ошибки в строках обрабатываются по согласованному правилу.

### Оценка задачи

- Текущая задача загружается из серверной очереди.
- Host может выбрать числовую карту SP.
- Выбор сохраняется на сервере.
- Итоговый SP фиксируется вручную.
- После фиксации доступен переход к следующей задаче.
- Обновление страницы не теряет подтверждённую оценку.

### Итоги

- Отображаются фактически оценённые задачи.
- Отображаются сохранённые итоговые SP.
- Неприменимые к одиночной оценке показатели отображаются прочерками.
- Отсутствие задач или ошибка получения итогов обрабатываются понятно.

## Порядок работы

1. Аналитик формирует черновик ключевых сценариев и критериев — 0,5–1 день.
2. Бэкенд/DevOps определяет серверные, контрактные и CI-проверки — параллельно, 0,5–1 день.
3. Фронтенды определяют клиентские проверки, smoke-набор и обработку ошибок — параллельно, 0,5–1 день.
4. Дизайнер готовит UI-чек-лист — параллельно, 0,5 дня.
5. Аналитик сводит материалы в единую стратегию и согласовывает её — 0,5 дня.
6. Тимлид актуализирует роадмап и принимает организационную часть — 0,5 дня.
7. Команда принимает стратегию; она применяется к задачам спринта 1.

## Критерии приёмки

- Описаны ключевые сценарии первого спринта и их ожидаемые результаты.
- Для каждой ключевой функции есть проверяемые критерии приёмки.
- Определены ручные и автоматические проверки.
- Указано, когда выполняется каждая проверка: локально, в PR, перед merge, перед демо, перед релизом.
- Назначены ответственные за каждый тип проверки.
- Определён минимальный регрессионный набор.
- Определён приоритетный перечень автоматизации для CI.
- Стратегия учитывает уровни L1/L2/L3 и DoD.
- Все роли подтвердили выполнимость и понятность стратегии.
- Аналитик принял результат; стратегия применяется к S1-01–S1-08.

## Definition of Done

- Документ размещён в репозитории, например `docs/testing-strategy.md`.
- Есть чек-листы для импорта CSV, оценки, итогов и восстановления состояния.
- Есть перечень обязательных проверок перед merge в `develop`.
- Есть перечень проверок, рекомендуемых для автоматизации в CI.
- Распределены ответственности между аналитиком, фронтендами, бэкендом/DevOps и дизайнером.
- Стратегия не требует настройки CI или Docker в рамках PRE-06.
- Документация обновляется при изменении правил разработки, API или ключевых сценариев.

## Риски

- Избыточное тестирование — команда потратит время на редкие случаи вместо первого сценария; приоритет — ключевой путь Host.
- Недостаточное тестирование интеграции — клиент и сервер могут работать по отдельности, но не вместе; обязательна интеграционная проверка.
- Размытая ответственность — проверки будут пропущены; за каждый тип проверки назначается конкретная роль.
- Поздняя автоматизация — риск накопления регрессий; уже в PRE-06 фиксируется минимальный набор для CI.
- Стратегия не актуализируется — назначить аналитика владельцем документа, а тимлида — ответственным за учёт тестовых работ в роадмапе.
