# ТЗ: PRE-05 — Исторические данные эталонов и подготовка исследования поиска

**Задача:** уточнить у заказчика формат, состав и доступность исторических оценённых задач, а также подготовить постановку исследования поиска похожих эталонов. Результат нужен до реализации L2-поиска в спринте 3, но начало работ не блокирует первый однопользовательский сценарий.

**Владелец задачи:** системный аналитик.

**Основной исполнитель исследования:** бэкенд-разработчик / DevOps.

**Участники:** тимлид (фронтенд-разработчик 1) — координация и актуализация роадмапа; фронтенд-разработчик 2 и дизайнер — требования к отображению эталонов; системный аналитик — требования, данные и критерии качества.

**Приоритет:** средний, но исследование нельзя откладывать до спринта 3: поиск эталонов и внешние интеграции являются рискованными направлениями и должны проверяться заранее.

## Цель

К концу задачи команда должна понимать, какие исторические данные доступны, в каком они формате, достаточно ли их для поиска, как будет измеряться релевантность и какой подход к поиску следует исследовать. Сам рабочий поиск в PRE-05 не реализуется.

**Ожидаемый результат по плану:** уточнены формат, состав и доступность исторических оценённых задач; выделены исследуемые методы поиска, критерии релевантности и способ проверки качества на доступных данных.

## Границы

| Входит | Не входит |
|---|---|
| Получение и анализ исторических данных | Реализация рабочего поиска |
| Описание формата и качества данных | Импорт эталонов в продуктивную модель |
| Постановка исследования поиска | Выбор и внедрение финального поискового движка |
| Кандидатские методы поиска | Оптимизация производительности поиска |
| Критерии релевантности и качества | Полный API поиска |
| Тестовый набор данных | Интеграция с YouTrack |
| Оценка рисков и объёма S3-03 | Реализация UI-карточек эталонов |

Исследование должно завершиться до начала L2-поиска в следующей итерации; в спринте 3 поиск должен возвращать реальные похожие эталоны — ориентир 3–5 задач с исходными SP и ссылками.

## Входные данные

Системный аналитик получает от заказчика и фиксирует:

- источник исторических задач: YouTrack, CSV-выгрузка, база данных или другой источник;
- количество доступных задач;
- период, за который собраны данные;
- наличие заголовков, описаний, приоритетов, меток, ссылок и вложений;
- наличие исторических оценок SP;
- качество и заполненность полей;
- язык задач;
- ограничения по передаче и хранению данных;
- формат выгрузки и возможность повторного получения обновлённых данных.

Если реальных данных пока нет, необходимо зафиксировать это как блокер и согласовать с заказчиком минимальный репрезентативный набор для исследования.

## Требования к эталонному набору

Для исследования нужен набор данных, позволяющий проверить поиск. Минимальные требования:

| Параметр | Требование |
|---|---|
| Количество задач | Достаточно для проверки поиска; конкретный минимум определяет аналитик по качеству данных |
| Обязательные поля | Заголовок, описание или содержательный текст, итоговый SP |
| Желательные поля | Приоритет, метки, тип задачи, ссылка YouTrack, дата создания |
| Качество | Задачи должны быть реально оценёнными и достаточно описанными |
| Язык | Зафиксировать язык или языки корпуса |
| Персональные данные | Удалить или обезличить чувствительные данные до передачи в репозиторий |

Для L2-поиска эталон должен отображаться с заголовком, SP, процентом сходства и описанием; интерфейс предусматривает 3–5 карточек рекомендаций.

## Постановка исследования

Бэкенд-разработчик / DevOps готовит исследование по единому сценарию:

1. **Подготовка данных:** загрузить выгрузку, оценить полноту полей, очистить дубликаты и некорректные записи.
2. **Базовая предобработка:** нормализация текста, обработка языка, выделение значимых полей.
3. **Кандидатские методы:** сравнить минимум два подхода, например:
   - полнотекстовый/лексический поиск;
   - векторный поиск по эмбеддингам;
   - гибридный подход: текстовый поиск + векторная близость + фильтры по меткам/приоритету.
4. **Тестовые запросы:** подготовить 10–20 репрезентативных задач для проверки.
5. **Оценка качества:** для каждого запроса зафиксировать найденные эталоны, их SP, ссылки и субъективную/согласованную оценку релевантности.
6. **Сравнение:** оценить точность, полноту, устойчивость к коротким заголовкам, зависимость от описания и стоимость реализации.
7. **Рекомендация:** выбрать подход для L2 и описать ограничения.

## Критерии релевантности

Аналитик фиксирует, что считается «похожей задачей». Рекомендуемые критерии:

- сходство предметной области по заголовку и описанию;
- совпадение типа работ или технической области;
- совпадение приоритета и/или меток как дополнительный сигнал;
- наличие известного итогового SP;
- наличие рабочей ссылки на YouTrack;
- отсутствие дубликатов в выдаче;
- ограничение выдачи 3–5 наиболее релевантными эталонами.

Нужно определить шкалу оценки: например, релевантно, частично релевантно, нерелевантно; либо числовую шкалу 0–2. Для принятия метода задать минимальный порог качества на тестовом наборе.

## Требования к результату поиска

Результат исследования должен описывать данные, необходимые интерфейсу для карточки эталона:

| Поле | Назначение |
|---|---|
| `title` | Заголовок похожей задачи |
| `description` | Краткое описание или фрагмент |
| `historical_sp` | Исходная оценка эталона |
| `similarity_score` | Процент/оценка сходства |
| `youtrack_url` | Ссылка на исходную задачу |
| `priority` | Приоритет, если доступен |
| `labels` | Метки, если используются в поиске |

Поиск не заменяет выбор команды: он только предоставляет подсказки.

## Распределение по ролям

### Системный аналитик — владелец PRE-05

**Задача:** получить требования и данные, поставить исследование и принять его результат.

- Уточнить у заказчика источник, объём, состав и доступность исторических задач.
- Зафиксировать обязательные и желательные поля эталонов.
- Определить правила очистки, обезличивания и хранения данных.
- Описать, что считается релевантным эталоном.
- Подготовить тестовые запросы и критерии оценки качества.
- Согласовать с бэкендом кандидатские методы поиска.
- Определить минимальные требования к результату для S3-03: 3–5 эталонов, SP, ссылка, сходство.
- Согласовать с дизайнером состав данных для карточки эталона.
- Принять исследование и зафиксировать выбранный подход для L2.
- Обновить аналитическую спецификацию и передать требования в S2-04/S3-03.

**Результат:** описание данных эталонов, постановка исследования, критерии качества и утверждённые требования к поиску.

### Бэкенд-разработчик / DevOps — исполнитель исследования

**Задача:** проверить данные и сравнить подходы к поиску.

- Получить выгрузку исторических задач и оценить её качество.
- Подготовить изолированный исследовательский набор данных; не размещать чувствительные данные в Git.
- Провести очистку: дубликаты, пустые описания, некорректные SP, битые ссылки.
- Реализовать экспериментальный прототип поиска вне основного приложения либо в отдельной исследовательской ветке.
- Сравнить минимум два подхода на одном тестовом наборе.
- Измерить качество выдачи по согласованным критериям.
- Оценить сложность реализации, зависимости, требования к хранению и производительность.
- Подготовить рекомендацию: какой подход использовать для L2 в S3-03.
- Зафиксировать риски: нехватка данных, слабые описания, языковые особенности, стоимость инфраструктуры.

**Результат:** исследовательский отчёт с сравнением методов, метриками, примерами выдачи и рекомендацией.

### Фронтенд-разработчик 1 — тимлид

**Задача:** координировать исследование и актуализировать роадмап.

- Согласовать с аналитиком сроки и приоритет исследования относительно задач спринта 1.
- Учесть исследование в дорожной карте и плане спринтов: PRE-05 → S2-04 → S3-03.
- Не назначать реализацию поиска до завершения исследования.
- Контролировать, что риски по данным и поиску своевременно эскалируются.
- При изменении сроков или объёма актуализировать `docs/roadmap.md` через PR.
- Принять организационную часть результата: понятно, кто, когда и с каким результатом продолжает работу.

**Результат:** актуализированный роадмап и согласованный план перехода от исследования к L2-поиску.

### Фронтенд-разработчик 2

**Задача:** определить требования к отображению эталонов.

- Проверить, какие поля нужны для карточки эталона: заголовок, SP, процент сходства, описание, ссылка.
- Описать требования к отображению длинных заголовков и описаний.
- Определить состояния: подсказки доступны, подсказки скрыты, нет релевантных эталонов, ошибка поиска.
- Согласовать с дизайнером поведение toggle «Скрыть подсказки».
- Передать аналитику требования к формату ответа поиска.

**Результат:** требования к UI-данным и состояниям блока «Похожие задачи из истории».

### Дизайнер

**Задача:** определить UX-требования к подсказкам.

- Проверить макет боковых колонок с эталонами на экране голосования.
- Определить состав карточки эталона и приоритет отображаемых полей.
- Описать поведение при 0, 1–2 и более 5 найденных эталонах.
- Определить отображение процента сходства и ссылки на YouTrack.
- Согласовать состояние «Скрыть подсказки» и его восстановление.
- Не проектирует алгоритм поиска, но фиксирует UX-ограничения для исследования.

**Результат:** UX-требования к карточкам эталонов и состояниям блока подсказок.

## Порядок работы

1. Аналитик запрашивает у заказчика данные и фиксирует требования — 0,5–1 день.
2. Бэкенд/DevOps оценивает качество данных и готовит исследовательский набор — 0,5–1 день.
3. Аналитик, фронтенд 2 и дизайнер согласуют критерии релевантности и состав карточки эталона — параллельно, 0,5 дня.
4. Бэкенд/DevOps проводит сравнение методов и готовит отчёт — 1–2 дня.
5. Аналитик оценивает результаты, выбирает подход для L2 и фиксирует требования — 0,5 дня.
6. Тимлид актуализирует роадмап и подтверждает план S2-04/S3-03 — 0,5 дня.
7. Аналитик принимает PRE-05.

## Критерии приёмки

- Подтверждён источник и фактическая доступность исторических данных.
- Описан формат данных: поля, типы, заполненность, язык, количество записей.
- Есть очищенный исследовательский набор данных.
- Определены критерии релевантности и шкала оценки качества.
- Подготовлено минимум 10 тестовых запросов.
- Сравнено минимум два метода поиска на одних и тех же данных.
- Есть примеры выдачи с эталонами, SP, сходством и ссылками.
- Есть рекомендация метода для L2-поиска и оценка рисков.
- Определены данные, необходимые UI для карточки эталона.
- Роадмап актуализирован тимлидом.
- Аналитик принял результат; команда может начать S2-04 без блокирующих вопросов.

## Definition of Done

- Исследовательский отчёт размещён в репозитории, например `docs/research/reference-search.md`.
- Данные эталонов не содержат секретов и чувствительной информации; реальные датасеты хранятся вне Git.
- Описаны источник данных, качество, ограничения и способ обновления.
- Сравнение методов выполнено на едином тестовом наборе.
- Зафиксированы критерии релевантности и минимальный порог качества.
- Есть рекомендованный подход для S3-03 и перечень необходимых доработок.
- Известно, что рабочий поиск не реализован в PRE-05; это явно указано в результате.
- Документация обновлена вместе с выводами исследования.

## Риски

- Недостаточно или низкое качество исторических данных — поиск не сможет дать полезные подсказки; нужен минимальный согласованный набор от заказчика.
- Слабые описания задач — заголовков может быть недостаточно для релевантного поиска; исследовать гибридный подход и метки.
- Неясные критерии релевантности — команда не сможет объективно выбрать метод; критерии фиксируются до экспериментов.
- Позднее обнаружение проблемы поиска — риск для S3-03; поэтому исследование начинается в подготовке, а завершается до L2-поиска.
- Утечка чувствительных данных — исторические выгрузки не коммитятся в репозиторий; используются обезличенные/локальные наборы.
