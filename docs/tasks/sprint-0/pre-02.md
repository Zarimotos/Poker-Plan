# ТЗ: PRE-02 — Логическая архитектура приложения

**Задача:** зафиксировать единую логическую схему Planning Poker: основные части системы, их ответственность, взаимодействия, движение данных и расположение общего состояния сессии. Результат нужен до реализации первого сквозного сценария спринта 1.

**Владелец задачи:** системный аналитик.

**Основные исполнители:** системный аналитик, бэкенд-разработчик / DevOps, 2 фронтенд-разработчика.

**Участник:** дизайнер — для проверки соответствия архитектуры пользовательским сценариям и экранам.

**Приоритет:** высокий; PRE-02 является зависимостью для PRE-03 и S1-01.

## Цель

К концу задачи команда должна понимать, из каких логических компонентов состоит продукт, кто за что отвечает, как данные перемещаются между клиентом и сервером и где хранится состояние сессии. Это позволит перейти к PRE-03 — модели данных и минимальным API-контрактам — без критических архитектурных неизвестностей.

**Ожидаемый результат по плану:** единая логическая схема системы с основными частями, назначением, ответственностью, взаимодействиями, движением данных и расположением общего состояния сессии.

## Границы

| Входит | Не входит |
|---|---|
| Логические компоненты клиента и сервера | Детальная техническая архитектура и выбор всех библиотек |
| Ответственности компонентов | Полная реализация кода |
| Взаимодействия и потоки данных | Полный API: это PRE-03 |
| Расположение состояния сессии | Настройка CI/CD и Docker |
| Схема первого вертикального среза | Проектирование всех отдалённых функций |
| Базовые принципы расширения до мультиплеера | Интеграция YouTrack и Excel |

Архитектура должна покрывать структуру, необходимую для первого вертикального среза: создание сессии → импорт CSV → очередь → оценка → подтверждение SP → итоги. Детали далёких функций проектируются позже.

## Обязательные решения

Системный аналитик вместе с разработчиками фиксирует:

- **Клиентская часть:** структура фронтенда, разделение экранов, состояния, работа с API и локальное состояние UI.
- **Серверная часть:** основные сервисы/модули, обработка запросов, хранение сессий, задач и оценок.
- **Общее состояние сессии:** где находится источник истины, какие данные хранятся на сервере, что кэшируется на клиенте.
- **Взаимодействие клиента и сервера:** HTTP-запросы для первого сценария; WebSocket закладывается как направление развития для синхронизации участников, но его полная реализация не требуется в спринте 1.
- **Жизненный цикл сессии:** создание, лобби, импорт задач, оценка, фиксация SP, переход к следующей задаче, итоги.
- **Обработка ошибок:** базовые сценарии сбоя запроса, отсутствующей сессии, невалидного CSV и недоступности сервера.
- **Восстановление состояния:** после обновления страницы сессия, задачи и подтверждённые оценки должны восстанавливаться из серверных данных.

## Целевая логическая схема

Рекомендуемая логическая модель для первого среза:

```text
Browser / Frontend
├── UI-слой: экраны и компоненты
├── Состояние UI: формы, загрузка, ошибки
└── API-клиент: запросы к серверу

Backend
├── API-слой: обработка запросов
├── Session Service: жизненный цикл сессии
├── Task Service: очередь и импорт задач
├── Estimation Service: выбор и фиксация SP
└── Storage: сессии, задачи, оценки

Данные
└── Серверное хранилище — источник истины
```

Для спринта 1 сервер является источником истины: сессия, очередь задач, выбранный SP и подтверждённый итоговый SP сохраняются на сервере. Клиент отображает актуальное состояние и отправляет действия пользователя.

## Потоки данных первого сценария

| Шаг | Действие пользователя | Клиент | Сервер | Результат |
|---|---|---|---|---|
| 1 | Создание сессии | Отправляет данные формы | Создаёт `Session`, генерирует идентификатор | Host попадает в лобби |
| 2 | Импорт CSV | Передаёт файл или распознанные задачи | Валидирует и сохраняет `Task` в очереди | Задачи появляются в сессии |
| 3 | Просмотр очереди | Запрашивает сессию | Возвращает задачи и их порядок | Host видит актуальную очередь |
| 4 | Выбор SP | Отправляет выбранный SP | Сохраняет оценку текущей задачи | Выбор зафиксирован |
| 5 | Подтверждение SP | Отправляет команду фиксации | Сохраняет итоговый SP | Можно перейти к следующей задаче |
| 6 | Итоги | Запрашивает результаты | Возвращает задачи и сохранённые SP | Host видит итоги |

Сценарий должен работать на реальных клиентских и серверных данных: создание сессии, импорт CSV, просмотр очереди, оценка, подтверждение SP и итоги.

## Требования к устойчивости

Архитектура должна заранее поддерживать:

- получение сессии повторно по серверному идентификатору;
- сохранение данных при обновлении страницы;
- понятную реакцию на сбой создания сессии, импорта, выбора SP и получения итогов;
- разделение клиентского состояния UI и серверного состояния сессии;
- последующее добавление участников и синхронного голосования без полного перепроектирования системы.

В S1-07 обновление страницы не должно удалять серверные данные сессии и подтверждённые оценки, а пользователь должен получать понятную реакцию на сбой ключевых операций.

## Распределение по ролям

### Системный аналитик — владелец PRE-02

**Задача:** сформировать логическую архитектуру и согласовать её с командой.

- Описать пользовательский сценарий первого среза и его границы.
- Определить основные логические компоненты и их ответственность.
- Описать жизненный цикл сессии и переходы между состояниями.
- Зафиксировать, какие данные являются серверными, а какие — локальными для UI.
- Описать потоки данных для создания сессии, импорта, очереди, оценки, подтверждения и итогов.
- Определить базовые ошибки и правила восстановления состояния.
- Согласовать схему с бэкендом и обоими фронтендами.
- Проверить, что архитектура не противоречит экранам и переходам из спецификации интерфейса.
- Передать утверждённую схему в PRE-03 как вход для модели данных и API-контрактов.

**Переход по файлам в репозитории на спецификацию ТЗ:** [`docs/specs/logical-architecture-specification.md`](docs/specs/logical-architecture-specification.md)

**Результат:** документ логической архитектуры с диаграммой компонентов, описанием потоков данных и жизненного цикла сессии.

### Бэкенд-разработчик / DevOps

**Задача:** предложить и согласовать серверную логическую структуру.

- Определить логические модули сервера: сессии, задачи, оценки, хранилище.
- Предложить способ хранения состояния сессии и обосновать его для первого среза.
- Описать границы ответственности API-слоя и бизнес-логики.
- Определить, какие операции должны быть атомарными или защищёнными от повторной отправки уже в базовой версии.
- Описать базовую обработку ошибок и коды/типы ошибок на уровне архитектуры.
- Оценить, как текущая схема будет расширяться до многопользовательской сессии в спринте 2.
- Подготовить требования к локальному запуску и структуре репозитория, если они влияют на архитектуру; создание самого репозитория — PRE-04 и зона тимлида.
- Дать заключение о реализуемости схемы и рисках.

**Результат:** серверная часть логической схемы, описание хранения состояния и предложения по устойчивости.

### Фронтенд-разработчик 1

**Задача:** определить клиентскую архитектуру и работу с сервером.

- Предложить структуру фронтенда: маршруты, экраны, общие компоненты, слой API-клиента.
- Определить, какие данные хранятся в глобальном состоянии клиента, а какие запрашиваются с сервера.
- Описать обработку состояний загрузки, ошибок и пустых данных.
- Предложить подход к восстановлению экрана после обновления страницы.
- Согласовать с бэкендом границы ответственности: клиент не дублирует сервер как источник истины.
- Оценить, как архитектура будет расширяться для WebSocket-событий и участия нескольких пользователей.

**Результат:** клиентская логическая схема, описание состояния UI и требований к API-клиенту.

### Фронтенд-разработчик 2

**Задача:** описать экранную модель и переходы в рамках архитектуры.

- Сопоставить логические компоненты с экранами: лендинг, создание сессии, лобби, импорт, очередь, оценка, подтверждение, итоги.
- Описать переходы между экранами и данные, необходимые каждому экрану.
- Определить общие UI-состояния: загрузка, ошибка, пустая очередь, отсутствие сессии.
- Проверить, что архитектура покрывает модалку импорта и предпросмотр задач.
- Согласовать с фронтенд-разработчиком 1 разделение ответственности между роутингом, состоянием и API-слоем.
- Передать замечания по UX-ограничениям аналитику и дизайнеру.

**Результат:** карта экранов → компоненты → данные → действия, согласованная с общей архитектурой.

### Дизайнер

**Задача:** проверить архитектуру на соответствие пользовательскому опыту.

- Проверить, что все экраны первого сценария и их переходы учтены в логической схеме.
- Указать обязательные UI-состояния: загрузка, ошибка, пустой список, подтверждение действия.
- Подтвердить, что модалка импорта, лобби и экран оценки не требуют архитектурных решений, противоречащих макетам.
- Обозначить, какие элементы будущих функций могут оставаться L1-каркасом и должны быть явно неактивны.
- Не проектирует серверную архитектуру, но участвует в согласовании пользовательских потоков.

**Результат:** замечания по пользовательским потокам и перечень обязательных UI-состояний.

## Порядок работы

1. Аналитик формирует черновик сценария, компонентов и потоков данных — 0,5–1 день.
2. Бэкенд предлагает серверную структуру и способ хранения состояния — параллельно, 0,5–1 день.
3. Фронтенды предлагают клиентскую структуру, маршруты и работу с состоянием — параллельно, 0,5–1 день.
4. Дизайнер проверяет соответствие пользовательским сценариям и UI-состояниям — параллельно, 0,5 дня.
5. Аналитик проводит согласование, устраняет противоречия и публикует финальную схему — 0,5 дня.
6. Команда принимает архитектуру; аналитик передаёт её в PRE-03.

## Критерии приёмки

- Есть диаграмма логических компонентов клиента, сервера и хранилища.
- Для каждого компонента описаны назначение и ответственность.
- Описаны все потоки данных первого пользовательского сценария.
- Зафиксировано расположение общего состояния сессии и источник истины.
- Описан жизненный цикл сессии от создания до итогов.
- Определены базовые ошибки и правила восстановления после обновления страницы.
- Архитектура допускает расширение до многопользовательского голосования в спринте 2.
- Бэкенд и оба фронтенда подтвердили реализуемость схемы.
- Аналитик принял результат; PRE-03 может начинаться без блокирующих вопросов.

## Definition of Done

- Логическая схема размещена в репозитории в читаемом формате, например `docs/architecture.md` и схема в `docs/`.
- Документ описывает только согласованный первый вертикальный срез, без попытки детализировать весь продукт.
- Все ключевые сценарии S1-01–S1-06 покрыты потоками данных.
- Известные ограничения явно указаны.
- Схема согласована аналитиком, бэкендом, обоими фронтендами и дизайнером.
- Изменения документов и схем внесены в репозиторий через PR согласно правилам совместной разработки.

## Риски

- Смешение UI-состояния и серверного состояния — приведёт к потере данных при обновлении страницы; устраняется явным разделением источника истины.
- Архитектура только под одного Host — может усложнить спринт 2; необходимо заранее предусмотреть участников, роли и синхронизацию.
- Преждевременная детализация — риск потратить время на API, БД и инфраструктуру, которые относятся к PRE-03 и последующим задачам.
- Разные представления о границах клиента и сервера — устраняется совместным согласованием потоков данных до начала PRE-03.
- Один бэкенд/DevOps становится узким местом — его задачи в PRE-02 нужно ограничить архитектурными решениями, а не реализацией.
