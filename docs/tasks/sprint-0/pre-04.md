# ТЗ: PRE-04 — Создание и настройка командного Git-репозитория

**Задача:** создать общий Git-репозиторий, предоставить доступ команде, настроить `main`/`develop`, защиту веток и правила Pull Request, а также проверить, что каждый участник может пройти полный цикл: ветка → изменения → PR → ревью → слияние.

**Владелец задачи:** фронтенд-разработчик 1 — тимлид.

**Основные исполнители:** тимлид, бэкенд-разработчик / DevOps, фронтенд-разработчик 2.

**Участники:** системный аналитик и дизайнер — для размещения и проверки проектных материалов.

**Приоритет:** высокий; репозиторий нужен для совместной разработки всех задач подготовки и спринта 1.

## Цель

К концу задачи команда получает рабочую инфраструктуру совместной разработки: репозиторий с доступами, двумя постоянными ветками, защитой от прямых изменений, едиными правилами коммитов и PR. Результат должен быть проверен на реальном тестовом изменении от каждого разработчика.

**По плану ожидаемый результат:** создан репозиторий с доступами команды, `main`/`develop`, защитой веток и правилами Pull Request; проверена возможность создать рабочую ветку, открыть PR, получить ревью и слить изменения.

## Границы

| Входит | Не входит |
|---|---|
| Создание репозитория и доступов | Реализация приложения |
| Ветки `main` и `develop` | Настройка CI/CD |
| Защита веток | Docker и развёртывание |
| Правила веток, коммитов и PR | Полная настройка тестового контура |
| Базовая структура `docs/` | Перенос всех исторических документов без необходимости |
| Размещение актуальной дорожной карты | Настройка продакшн-окружения |

Начальная настройка репозитория не требует готового приложения или CI.

## Требования к репозиторию

### Ветки

Используется упрощённый GitFlow с двумя постоянными ветками:

| Ветка | Назначение | Правила |
|---|---|---|
| `main` | Только принятые версии продукта | Прямой push и перезапись истории запрещены |
| `develop` | Интеграция изменений текущей разработки | Должна собираться; прямые push запрещены |

Рабочие ветки создаются от `develop`, а перенос в `main` выполняется только для принятого релиза.

### Рабочие ветки

- Отдельная задача — отдельная ветка.
- Ветки создаются от актуальной `develop` и сливаются через PR.

### Имена веток

Формат: `type/short-description`; при наличии трекера можно добавить ID задачи.

Примеры:

- `feat/session-creation`
- `feat/csv-import`
- `docs/project-roadmap`
- `chore/repo-setup`
- `test/csv-validation`

Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.

### Коммиты

Используется Conventional Commits:

```text
type(scope): description
```

Примеры:

```text
feat(session): add session creation endpoint
docs: update local setup guide
chore: configure linting
test(import): cover invalid CSV rows
```

При Squash and merge итоговое сообщение в `develop` должно отражать содержание всей задачи, а не последний промежуточный коммит.

### Pull Request

Для каждого изменения в `develop` создаётся PR из рабочей ветки.

Обязательные правила:

- минимум одно одобрение другого разработчика;
- автор не утверждает собственный PR;
- блокирующие замечания устраняются до слияния;
- в PR указываются цель, реализованное поведение, способ проверки и известные ограничения;
- для UI-изменений по возможности прикладывается скриншот или краткое описание демонстрации;
- изменения API-контрактов, моделей данных и соглашений об интеграции согласуются с затронутыми разработчиками до слияния;
- для рабочих веток применяется Squash and merge.

### Защита веток

Для `main` и `develop` необходимо включить:

- запрет прямого push;
- запрет force push и перезаписи истории;
- обязательное прохождение настроенных проверок перед слиянием;
- требование минимум одного одобрения для PR;
- запрет обхода правил без согласованной процедуры.

## Базовая структура репозитория

Минимальная структура на старте:

```text
/
├── README.md
├── docs/
│   ├── roadmap.md
│   ├── architecture.md
│   ├── data-model.md
│   └── api.md
├── frontend/
├── backend/
└── .gitignore
```

Точные папки `frontend/` и `backend/` могут быть скорректированы под выбранный стек, но структура должна сразу разделять код, документацию и настройки.

В `docs/` размещаются читаемые и редактируемые материалы: дорожная карта, архитектурные схемы, API-контракты, описания интеграций и соглашения по тестированию.

## Безопасность

- Токены, пароли, приватные ключи и реальные секреты не размещаются в репозитории.
- Для локальных настроек используется шаблон, например `.env.example`.
- Реальные значения окружения хранятся вне Git в согласованном командой менеджере секретов или локально.
- Доступ к репозиторию выдаётся только участникам команды по минимально необходимым ролям.

## Проверочный сценарий

После настройки каждый разработчик должен выполнить тестовый цикл:

1. Склонировать репозиторий.
2. Создать рабочую ветку от `develop`.
3. Внести небольшое изменение, например добавить своё имя в `docs/team.md` или тестовый файл.
4. Сделать коммит по Conventional Commits.
5. Отправить ветку в удалённый репозиторий.
6. Открыть PR в `develop`.
7. Получить ревью и одобрение другого разработчика.
8. Выполнить Squash and merge.
9. Убедиться, что изменения появились в `develop`.

Проверка должна подтвердить, что прямой push в `main` и `develop` заблокирован.

## Распределение по ролям

### Фронтенд-разработчик 1 — тимлид, владелец PRE-04

**Задача:** создать и настроить репозиторий, обеспечить доступ, правила работы и актуальную дорожную карту.

- Создать удалённый Git-репозиторий.
- Выдать доступ всем участникам команды с подходящими ролями.
- Инициализировать репозиторий: README, `.gitignore`, базовая структура каталогов.
- Создать и запушить `main` и `develop`.
- Настроить защиту обеих постоянных веток.
- Настроить правила PR: ревью, запрет self-approval, Squash and merge.
- Определить и зафиксировать шаблон PR.
- Разместить в `docs/roadmap.md` актуальную дорожную карту разработки и поддерживать её актуальность.
- Координировать техническую декомпозицию, интеграцию и распределение задач между исполнителями.
- Провести проверочный цикл с каждым разработчиком.
- Принять результат и объявить репозиторий готовым к работе.

**Результат:** работающий репозиторий с доступами, защищёнными ветками, утверждёнными правилами PR и актуальной дорожной картой в `docs/`.

### Бэкенд-разработчик / DevOps

**Задача:** подготовить техническую основу репозитория.

- Согласовать с тимлидом структуру монорепозитория либо раздельных репозиториев.
- Подготовить `.gitignore` для серверного стека, локальных конфигураций, секретов и артефактов сборки.
- Подготовить `.env.example` без реальных секретов.
- Проверить, что структура `backend/` не мешает будущему локальному запуску и развёртыванию.
- Проверить правила веток и PR на тестовом изменении.
- Подготовить предложения по будущим проверкам качества, не настраивая CI в рамках PRE-04.
- Помочь тимлиду с настройкой доступов и защиты веток.

**Результат:** техническая структура репозитория, `.gitignore`, `.env.example`, подтверждение работоспособности Git-процесса.

### Фронтенд-разработчик 2

**Задача:** подготовить клиентскую часть структуры и проверить совместную работу.

- Согласовать с тимлидом структуру `frontend/` под выбранный стек.
- Подготовить базовый `.gitignore` для зависимостей, сборки, локальных настроек и файлов редактора.
- Проверить, что можно создать ветку, внести изменение, открыть PR и пройти ревью.
- Проверить понятность правил коммитов, веток и шаблона PR.
- Участвовать в ревью тестового PR другого разработчика.
- Сообщить о проблемах доступа, прав или защиты веток.
- При необходимости добавить базовый README для запуска фронтенда; полноценная настройка окружения не входит в PRE-04.

**Результат:** структура `frontend/`, `.gitignore`, успешный тестовый PR и подтверждение работоспособности процесса.

### Системный аналитик

**Задача:** разместить аналитические и технические документы в репозитории.

- Перенести в `docs/` актуальные версии плана спринтов, аналитических материалов, спецификаций и требований — в читаемом формате.
- Создать или согласовать структуру документации: `architecture.md`, `data-model.md`, `api.md`.
- Указать статус документов и ссылки на актуальные внешние материалы, например Figma.
- Далее поддерживать документы актуальными при изменении требований, моделей данных или API.
- Не отвечает за техническую настройку Git и дорожную карту.

**Результат:** структура `docs/` и размещённые актуальные аналитические материалы.

### Дизайнер

**Задача:** обеспечить доступ к дизайну и правилам ссылок на него.

- Передать тимлиду или аналитику ссылку на актуальный Figma-файл и определить его статус.
- Согласовать, где в `docs/` будет храниться ссылка на дизайн и краткое описание макетов.
- Не размещает в Git тяжёлые экспорты без необходимости.
- Проверяет, что в README или `docs/` понятно, где находится актуальный дизайн.

**Результат:** ссылка на актуальный дизайн и соглашение о его расположении в документации.

## Порядок работы

1. Тимлид создаёт репозиторий, выдаёт доступы, создаёт `main`/`develop` и размещает дорожную карту — 0,5–1 день.
2. Бэкенд/DevOps готовит техническую структуру, `.gitignore`, `.env.example` — параллельно, 0,5 дня.
3. Фронтенд 2 согласовывает структуру клиентской части и готовит базовые файлы — параллельно, 0,5 дня.
4. Аналитик размещает документы в `docs/` — параллельно, 0,5 дня.
5. Дизайнер передаёт ссылку на Figma и согласовывает её размещение — параллельно, 0,5 часа.
6. Тимлид, бэкенд и фронтенд 2 проходят тестовый цикл: ветка → PR → ревью → merge — 0,5 дня.
7. Тимлид принимает PRE-04.

## Критерии приёмки

- Репозиторий создан и доступен всем участникам команды.
- Есть ветки `main` и `develop`.
- Прямой push, force push и обход защиты в `main`/`develop` заблокированы.
- Рабочие ветки создаются от `develop` и сливаются только через PR.
- Для PR требуется минимум одно стороннее одобрение.
- Правила имён веток и Conventional Commits зафиксированы в документации.
- Шаблон PR создан и используется.
- Есть базовая структура `docs/`, README и `.gitignore`.
- Актуальная дорожная карта размещена в `docs/roadmap.md` и поддерживается тимлидом.
- Секреты не попадают в репозиторий; есть `.env.example`.
- Тимлид, бэкенд/DevOps и фронтенд 2 успешно прошли тестовый цикл: ветка → коммит → PR → ревью → Squash and merge.
- Тимлид принял результат.

## Definition of Done

- Репозиторий доступен, защищён и готов к совместной разработке.
- `develop` собирается и содержит базовую структуру проекта.
- Все разработчики подтвердили возможность работы по процессу.
- Документация по Git-процессу и дорожная карта размещены в репозитории.
- Известные ограничения явно указаны: CI, Docker и развёртывание не входят в PRE-04.
- Все изменения внесены через PR согласно установленным правилам.

## Риски

- Совмещение роли тимлида и фронтенд-разработчика — тимлид может стать узким местом; техническую подготовку структуры и `.gitignore` делегируем бэкенду/DevOps и фронтенду 2.
- Неправильные права доступа — участник не сможет создать ветку или пройти PR; проверяется тестовым циклом для каждого разработчика.
- Слабая защита веток — появится риск прямых изменений в `develop` или `main`; защита включается до начала разработки.
- Дорожная карта не актуализируется — назначен единственный владелец: тимлид; изменения сроков и объёма фиксируются в `docs/roadmap.md`.
- Документация вне репозитория — приведёт к рассинхрону требований; после создания репозитория актуальные версии документов хранятся в нём.
